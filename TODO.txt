3) Why template? Why extdata? What do they do? Maybe delete them?

    Both load-bearing, don't delete. templates/tutorial.qmd is
    create_tutorial()'s starter file. extdata/ holds the vendored
    quarto-live extension (makes format: live-html render at all) and our
    own quiz.js/quiz.css (the runtime behind question(), quiz(),
    student_info(), download_answers_button()). Delete either and
    rendering, or every widget, silently breaks. The extdata/templates
    names are just conventional R package folder names, not something R
    enforces -- purely for readability.

8) After the student hits the download button, can we add a hash to the download answers. This hash would be created from info like date/time, computer name, user name, and so on. The teacher, of course, needs to be able to translate the hash. But the hash is designed so that, even though students know what it is, they can't easily add an appropriately constructed hash to their answers. This is not perfect security, but it is pretty good.

    Done, but reframed after confirming two things: browser JS can't read
    computer name, OS username, or run whois -- no way around that -- so
    those fields aren't included. And with no server, there's no secret key
    only the teacher has, so this is tamper-EVIDENCE, not proof of identity:
    it stops quietly editing a wrong answer before turning the file in, not
    a technical student reverse-engineering the hash.

    download_answers_button() now embeds a metadata block (timestamp,
    timezone, browser info, a per-device id) plus a SHA-256 hash over the
    content. verify_submission(path) recomputes it and reports OK vs.
    TAMPERED, and also checks the visible content matches what was hashed.

    Verified for real: downloaded a file, verified it OK, hand-edited it,
    and confirmed verify_submission() caught it. Tests in
    tests/js/quiz.spec.js and tests/testthat/test-submission.R.

Big Picture: We hope to replace both learnr and tutorial.helpers with learnr2. There is no reason to have two packages, or to not have learnr2 do everything we want a tutorial package to do.

DK: Consider providing a simple hash to guarantee that students haven't cheated, even if they submit html. The function would run some R code which produced a string including things like date, time, pwd, whois, computer name, and whatever else. It then takes that string and turns it into a hash. That hash is output into the html. If there are concerns about cheating, an instructor can check the hash. He can run some code on the HTML answer file and get back that information in an easy to read form.

Perhaps the the code first creates a JSON file --- or rather text string --- which is a paired list of command (or request) and result. So:

date, 2026-05-19

And so on. A JSON list would be nice because, after unhashing, it is easy to process. Also, if some commands (or requests) don't work on some OSs, that would be OK. The JSON file would just contain:

pwd, NULL

or whatever.
