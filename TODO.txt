    Done. Verdict: clear instructions beat a bare template -- a template
    shows what correct output looks like once, not why (the echo: false
    chunk-scoping rule, the "no local R/RStudio" translation trap, and
    "verify by rendering" as a habit are all things a template can't teach,
    and CLAUDE.md already documented a real regression proving it).

    Added AGENTS.md, recording that verdict plus the two follow-ups:
    create_tutorial() is kept -- few humans will call it, but it's exactly
    the kind of single unambiguous action an AI agent benefits from reaching
    for instead of hand-typing frontmatter. student_info() is a different
    kind of question entirely: it's tutorial *content* (like question()/
    quiz()), called from inside the .qmd regardless of how that .qmd came to
    exist, not an authoring-time tool -- so "templates vs. instructions"
    doesn't apply to it the way it does to create_tutorial().

    Tested by hand-authoring inst/tutorials/intro-vectors/intro-vectors.qmd

    CLAUDE.md was left untouched (still has the original authoring/

    Follow-up question worth heading off: does this verdict mean the
    template (inst/templates/tutorial.qmd, scaffolded by create_tutorial())
    should just be deleted? No -- that was never the verdict. "Templates
    can't teach" is not the same claim as "templates are worthless."
    AGENTS.md is the primary guide because only written instructions can
    explain the *why* behind a rule; the template's remaining job is a
    plain scaffolding convenience -- a guaranteed-correct starting point,
    saving a human or an AI agent from hand-typing frontmatter or
    forgetting add_live_extension(). Deleting it would also just break
    create_tutorial() outright, since it reads the template via
    system.file() -- not a documentation question, a real regression.

    Open gap, found while verifying this (not fixed yet, on request --
    left as a comment instead): actually downloaded a real answers file
    after pasting an image and checked its contents. The pasted image
    itself is never in it -- collectAnswers() in quiz.js only writes
    hasImage: true/false, never the image data, even though the image is
    sitting right there in localStorage. So today, an instructor who
    downloads a student's answers cannot see the screenshot the student
    pasted, only that one was attached; the student's typed description is
    the only thing anyone actually reading the JSON sees.

    Just embedding the raw image bytes wouldn't fully fix this either --
    a JSON file with a base64 blob in it isn't something a human can look
    at without extra tooling. The real fix is two parts: (1) have
    collectAnswers() include the actual image data URI, and (2) add an R
    helper alongside verify_submission() -- something like
    extract_submission_images(path, dir) -- that pulls any embedded images
    out of a downloaded JSON into real .png files an instructor can just
    open, the same way verify_submission() already turns the integrity
    hash into a plain-English report instead of leaving a human to check
    it by hand.
