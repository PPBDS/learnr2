0) I like that tutorials pop up in the VS Code editor. Make sure to document how that is happening?

    Partial answer, re: why it's sometimes VS Code and sometimes a
    separate browser tab (inconsistent, not something we've made
    deliberately configurable). Checked httpuv::runStaticServer() (what
    run_tutorial() now calls to serve+open a tutorial) directly:

        if (isTRUE(browse)) {
          utils::browseURL(paste0("http://", host, ":", port))
        }

    That's the entire mechanism on our side -- plain utils::browseURL(),
    nothing httpuv- or learnr2-specific, no VS Code awareness at all.
    Where that actually opens is decided entirely by R's
    options("browser") in whichever R session happens to execute it:

    - Base R's default is essentially "hand it to the OS," which opens a
      new tab/window in the system's default browser.
    - VS Code's R extension overrides this per session: when it attaches
      to an R session it manages (its own "R Terminal"), an init script
      sets options(browser = <its own VS Code webview handler>), so
      browseURL() gets redirected into a Simple Browser panel inside VS
      Code instead.

    So "sometimes VS Code, sometimes a separate tab" isn't random -- it's
    telling us which R process actually executed run_tutorial() at that
    moment: the hooked R Terminal the VS Code R extension manages, vs. any
    other R process (a plain Rscript call, a background job, a fresh
    session the extension hasn't hooked yet, or the separate "R Tutorials"
    extension possibly launching things through its own mechanism rather
    than the hooked Terminal).

    Not yet confirmed: exactly how the "R Tutorials" VS Code extension
    itself launches a tutorial -- that's the extension's own source, which
    wasn't available to inspect from this session. That's the remaining
    piece needed to fully document "how that is happening," and to decide
    whether to just force a specific target from run_tutorial() itself
    (e.g. always open a real browser tab, or always try the VS Code
    webview) regardless of which R session is running it.

5) hello-learnr to does not download the answers for the execute code questions. It should.

    Done. Confirmed the gap first: collectAnswers() in quiz.js only ever
    scanned .learnr2-question/.learnr2-info elements -- {webr} exercises
    are entirely quarto-live's own markup, with no learnr2-side registry
    of what exercises exist on a page at all, so they were silently never

    Fixed by reading quarto-live's own bundled source (live-runtime.js,
    webr-exercise.ojs) rather than guessing:
    - Every {webr} cell embeds a `<script type="webr-<block-id>-contents">`
      tag with base64-encoded JSON of its chunk options and starter code --
      present in the static HTML regardless of whether WebR has finished
      booting, so exercises can be discovered without needing a live
      runtime.

      label is only there for the human-readable id in the download.
    - Only cells with `#| persist: true` can be captured at all -- that's
      the only condition under which quarto-live's own editor ever writes

      limit of quarto-live's editor, not a choice learnr2 makes.

12) Keep in mind that students use Mac, Windows, Chromebooks and so on. Does a screenshot always get saved as a PNG file? How does the Clipboard keep track of that fact?

    Done. Short answer: no, not guaranteed -- so allow_image no longer
    assumes it. The mechanism: an OS screenshot goes onto the system
    clipboard in some native, platform-specific format (bitmap, TIFF,
    etc.); the reader's browser is what translates that into something a
    web page can read at all, via a "clipboard item" carrying a MIME
    `.type` string. quiz.js reads this through the paste event's
    `clipboardData.items` (chosen originally since it works without the
    permission prompt the newer Async Clipboard API needs).

    Checked what's actually documented (MDN, web.dev) before assuming
    anything: only the *write* side of the newer Async Clipboard API is
    documented as PNG-only for images. There's no equivalent documented
    guarantee for the older paste-event path this code actually uses, and
    a real OS-native screenshot's exposed format is platform-dependent --
    this could not be verified end-to-end against real macOS/Windows/
    ChromeOS screenshot tools from this sandbox (no way to trigger a
    genuine OS-level screenshot here, only simulate paste events).

    Given that, stopped depending on the assumption entirely instead of
    continuing to guess: allow_image now accepts PNG, JPEG, GIF, WebP, or
    BMP -- whatever raster type the clipboard actually hands over -- and
    re-encodes it as PNG itself (via an off-DOM <img>/<canvas> round-trip)
    before storing it. What's saved is now always genuinely PNG,
    regardless of the source format, so the platform question stops
    mattering. Deliberately excludes image/svg+xml (vector markup, not a
    screenshot, different security surface) and image/tiff (a real
    possibility on macOS specifically, but mainstream browsers other than
    Safari generally don't decode TIFF via <img> either, so accepting it
    would just trade one confusing failure for another -- flagged as an
    open gap rather than silently papered over).

    Verified two ways: Playwright (updated the old "non-PNG image is
    rejected" test, since GIF is now accepted-and-converted rather than
    rejected -- confirmed the stored data URL is genuinely
    data:image/png;... via its magic-byte prefix, not just relabeled; kept
    a rejection test for genuinely non-image content instead), and a real
    rendered hello-learnr2 in a browser -- pasted an actual GIF file
    object, confirmed no error and a real PNG-signature data URL came out
    the other side. All 34 JS tests pass.
